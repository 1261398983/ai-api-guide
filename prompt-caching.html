省钱机制 · 2026-11-07

Prompt Caching 怎么用才真省钱

写了 cache_control 不等于命中。大多数人一次都没命中过，还白付了写入溢价。

缓存省的是哪一笔钱

模型每次请求都要把你发过去的全部内容"读一遍"，这部分叫输入 token。 对话越长、文件越大，输入 token 越多——而且每轮都要重付一次。

Prompt caching 的思路：把不变的那一段存起来，下次只付读取的钱。

类型相对价格什么时候发生
普通输入1×没有被缓存的输入
缓存写入约 1.25×第一次请求，把前缀写进缓存
缓存读取约 0.1×后续请求命中同一前缀

倍数以各服务商当前定价为准，不同模型、不同有效期会有差异。 但量级关系不变：命中一次省的钱，远大于写一次缓存的溢价——前提是你真的命中。

三个条件必须同时满足

条件含义怎么违反的
前缀完全一致逐字节匹配，一个空格都算不同把时间戳、随机 ID、文件名放进前缀
长度达到下限太短的块不会缓存把一段 200 字的说明标记成缓存
在有效期内分钟级 TTL，过期要重写隔一小时才发第二次请求

第一条是最常见的失败原因。缓存不是"相似就命中"，是"前面一模一样才命中"。

cache_control 怎么写

以 Anthropic 协议为例，把标记加在要缓存的内容块上：

{
  "model": "claude-sonnet-4-20250514",
  "system": [
    {
      "type": "text",
      "text": "（这里放不变的规则、文档、示例，越长越值）",
      "cache_control": { "type": "ephemeral" }
    }
  ],
  "messages": [
    { "role": "user", "content": "这次的具体问题放这里" }
  ]
}

关键：标记的那一块必须真的不变。把动态内容放在它后面，而不是里面。

---

用户问题：这段为什么报错？        ← 不标记

怎么验证真的命中了

这是大多数人漏掉的一步。不看 usage 字段，你根本不知道有没有省到钱。

响应里有两个关键字段：

字段含义
cache_creation_input_tokens本次写进缓存的 token 数（付 1.25×）
cache_read_input_tokens本次从缓存读的 token 数（付 0.1×）
 
curl -s https://your-endpoint.example.com/v1/messages \
  -H "x-api-key: 你的Key" \
  -H "anthropic-version: 2023-06-01" \
  -H "content-type: application/json" \
  -d @payload.json | jq '.usage'

期望输出：

{
  "input_tokens": 128,
  "cache_creation_input_tokens": 0,
  "cache_read_input_tokens": 8420,
  "output_tokens": 356
}

判读方法：

  • 第一次请求：cache_creation 大、cache_read 为 0（正常，在写）
  • 第二次起：cache_read 大 → 命中
  • 两次都是 0 → 前缀有问题，或者端点不支持
  • 一直 cache_creation 很大而 read 为 0 → 每次都重写缓存，比不缓存更贵

最后一种是最坏的情况：你以为在省钱，实际多付了 25%。

走中转站的三个坑

这是本文和大多数教程不一样的地方。用官方端点时缓存行为是确定的，走中转时不一定。

坑一：不透传 cache_control

网关把请求转发给上游时，如果只挑它认识的字段，cache_control 会被丢掉。 结果：你发了标记，上游根本没收到，缓存永远不生效。

验证：连发两次相同请求，看 cache_read_input_tokens 是否大于 0。

坑二：改写了请求体

有些网关会"规范化"请求——重排 JSON 字段、补默认值、注入自己的系统提示。 只要前缀变了，缓存就废了。

验证：如果能拿到网关的调试日志或让运营方确认是否改写。

坑三：透传了但不按缓存价计费

最隐蔽的一个。上游按缓存价收它 0.1×，网关按普通输入价收你 1×—— 你在 usage 里看到命中，账单却没降。

验证：算一笔。cache_read_input_tokens × 该模型单价 × 你的倍率， 和实际扣费对一下。差得多就是没按缓存价算。

# 快速对账：两笔请求的差额
# 第二次请求的 cache_read 很大，但扣费和第 0 次差不多 → 没按缓存价算

什么时候缓存没用

场景为什么没用
每次问的问题完全不同、没有共同前缀没有可复用的部分
内容很短（几百 token）达不到缓存下限，省的钱覆盖不了复杂度
请求间隔超过 TTL每次都重新写，只付溢价不享折扣
一次性的批处理同一前缀只会用到一次
前缀里有时间戳 / 会话 ID每次不同，永远命不中

判断标准很简单：同一段内容在 5 分钟内会不会被重复发送？会，才值得缓存。

能省多少：一个算例

假设：系统规则 + 项目文档共 8000 token，一次会话里问 10 轮。

情况输入 token 计费量
不缓存8000 × 10 = 80,000
缓存，只命中 1 次8000×1.25（写） + 8000×0.1×1（读） + 8000×8（未命中）= 74,800
缓存，第 2 轮起全命中8000×1.25 + 8000×0.1×9 = 17,200

全命中时，输入部分的账单降到原来的 21%。 只命中一次时几乎没省——这就是为什么"写了 cache_control"和"真省钱"是两件事。

算例只计算输入侧，输出 token 不受缓存影响，按原价计。
