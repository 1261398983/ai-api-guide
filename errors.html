先记住一条：401 和 429 是最高频的两个错误，占了新手问题的八成。先把这两节读完，剩下的按需查。

401 Unauthorized —— 九成是变量名写错

症状

{"type":"error","error":{"type":"authentication_error","message":"invalid x-api-key"}}

或者更模糊的：

Error: 401 {"code":"INVALID_API_KEY","message":"Invalid API key"}

根因排序

#原因怎么确认
1变量名写错：[CC] 读 ANTHROPIC_AUTH_TOKEN，不是 ANTHROPIC_API_KEY看下面的检查命令
2值里带了空格或引号echo 出来看长度
3写在 .bashrc 但没 source新开终端再 echo
4key 被吊销 / 过期控制台看密钥状态
5复制时漏了 sk- 前缀长度对比

验证命令

# Linux / macOS
echo "[$ANTHROPIC_AUTH_TOKEN]"
echo "${#ANTHROPIC_AUTH_TOKEN}"     # 长度，正常 40+ 或 100+

# Windows PowerShell
echo "[$env:ANTHROPIC_AUTH_TOKEN]"
($env:ANTHROPIC_AUTH_TOKEN).Length

方括号是为了看有没有首尾空格。一个尾随空格就能让 key 失效。

直接用 curl 排除客户端问题

curl https://api.97wl.cc/v1/models \
  -H "Authorization: Bearer sk-你的密钥"

curl 能通、客户端不通 → 是客户端变量名的问题，不是 key 的问题。

402 / insufficient_quota —— 余额与额度的区别

两种完全不同的 402

响应体关键字段含义修法
insufficient_quota账户额度用完了充值
billing_hard_limit_reached碰到你设的消费上限调高上限，或等下月
insufficient_user_quota中转站侧余额不足站内充值
注意：很多站把额度耗尽也返回 429，不是 402。看到 429 先看响应体的 type，不要一上来就降并发。

403 Forbidden —— 三个不同来源

来源典型响应修法
地区限制country, region, or territory not supported换出口节点；中转站一般已处理
密钥权限permission denied for this model密钥绑定的分组里没有这个模型
IP 白名单ip not allowed把当前出口 IP 加进白名单，或关掉白名单

第三项最容易踩：给密钥开了 IP 白名单，然后换了网络（比如从家里切到公司），所有请求都 403。

404 Not Found —— 几乎都是 base_url 的问题

最经典的一个错误

客户端base_url 应该写
[CC]（Anthropic 协议）https://api.example.com  不带 /v1
[OI] SDK / Cursor / Cherry Studiohttps://api.example.com/v1  带 /v1

写反了就是 404。因为：

  • Anthropic 协议自己拼 /v1/messages，你带 /v1 就变成 /v1/v1/messages
  • [OI] SDK 自己拼 /chat/completions，你不带 /v1 就变成 /chat/completions

另一种 404：模型名不存在

{"error":{"message":"model not found: gpt-4o-latest","type":"invalid_request_error"}}

先拉模型列表对一遍：

curl https://api.example.com/v1/models \
  -H "Authorization: Bearer sk-你的密钥" | grep -o '"id":"[^"]*"'

413 Payload Too Large

单次请求体超过服务端上限。中转站的上限通常比官方低（因为要过一层反代）。

  • 检查 Nginx 的 client_max_body_size（默认只有 1M）
  • 长文档先切分再逐段处理
  • 图片走多模态接口而不是 base64 塞进文本

429 Too Many Requests —— 分清楚是哪一种

先看响应体

# 情况 A：真限流
{"error":{"type":"rate_limit_error","message":"Rate limit reached for requests"}}

# 情况 B：额度耗尽（伪装成 429）
{"error":{"type":"insufficient_quota","message":"You exceeded your current quota"}}

# 情况 C：并发超限
{"error":{"type":"rate_limit_error","message":"concurrent requests limit exceeded"}}
类型修法
A 请求频率降 QPS，加退避重试（指数退避 + 抖动）
B 额度充值，降并发没用
C 并发降 --concurrency，或用队列串行

正确的重试写法

async function withRetry(fn, max = 4) {
  for (let i = 0; i < max; i++) {
    try { return await fn(); }
    catch (e) {
      if (e.status !== 429 && e.status < 500) throw e;
      const base = Math.min(8000, 500 * 2 ** i);
      const jitter = Math.random() * 300;
      await new Promise(r => setTimeout(r, base + jitter));
    }
  }
  throw new Error('retries exhausted');
}

不要对 400/401/402/403/404 重试——这些是确定性错误，重试只会浪费额度。

500 / 502 / 503 / 504 —— 上游的问题

码含义该做什么
500上游内部错误重试；持续出现就换模型
502网关收到无效响应同上，通常几秒内自愈
503上游暂时不可用等 30 秒再试
504网关等待超时缩短请求、降低 max_tokens

504 的特殊处理

504 往往不是上游慢，而是你的反代超时比上游短。Nginx 默认 proxy_read_timeout 是 60 秒，长输出很容易超。

location /v1/ {
    proxy_read_timeout 300s;
    proxy_send_timeout 300s;
    proxy_buffering off;      # 流式响应必须关
}

529 Overloaded（Anthropic 专有）

{"type":"error","error":{"type":"overloaded_error","message":"Overloaded"}}

Anthropic 服务端过载。不是你的问题，也不扣费。处理方式：

  • 指数退避重试（1s → 2s → 4s → 8s）
  • 降低并发，不要硬刷
  • 持续 529 说明这个时段上游紧张，换时段或换模型

模型侧错误（HTTP 200 但内容异常）

字段含义修法
stop_reason: "max_tokens"输出被截断调大 max_tokens
stop_reason: "length"同上（[OI] 风格）同上
context_length_exceeded输入超上下文切分历史，开新会话
content_filter内容被拦改写提示词

一个 30 秒的自检脚本

#!/usr/bin/env bash
# 依次验证：连通 → 鉴权 → 模型 → 对话
BASE="${1:-https://api.97wl.cc}"
KEY="${2:?usage: check.sh BASE KEY}"

echo "1) 连通性"
curl -s -o /dev/null -w "  HTTP %{http_code}  %{time_total}s\n" "$BASE/"

echo "2) 鉴权"
curl -s -o /dev/null -w "  HTTP %{http_code}\n" "$BASE/v1/models" \
  -H "Authorization: Bearer $KEY"

echo "3) 对话"
curl -s "$BASE/v1/chat/completions" \
  -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"你的模型名","messages":[{"role":"user","content":"hi"}],"max_tokens":8}' \
  | head -c 300
echo

三步分别失败，就分别对应：网络问题、key 问题、模型或参数问题。
