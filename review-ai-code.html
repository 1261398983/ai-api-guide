AI 写的代码怎么验收

逐行读是效率最低的做法。AI 的毛病有固定模式，按模式查比按行查快十倍。

为什么不能逐行读

AI 写的代码，可读性通常比人写的更好——命名规范、结构清晰、注释齐全。 所以你逐行读的时候，会不断得到"这写得挺对"的反馈。

问题恰恰在这里：它的错误不在行内，在行与行之间、文件与文件之间。

局部看每一行都对，整体却漏了三个调用方。这种错误逐行读永远发现不了。

正确的验收方式是按缺陷模式查，不是按代码行读。

五类系统性缺陷

下面五类是 AI 生成代码的高频问题，按出现频率排序。每一类都有对应的快速检查手段。

一、只改被点到的地方

最常见，也最容易造成编译错误。改一个被多处引用的函数签名，它只改定义处； 给一个模型加字段，它只改结构体不改序列化。

检查手段：改完立刻用 grep 搜被改动的标识符，数一下还有多少处引用没动。

# 改了几个函数/字段，就搜几个
grep -rn "旧函数名" --include=*.py .
grep -rn "old_field_name" --include=*.go .
grep -rn "OldType" --include=*.ts .

二、编造不存在的 API

调用一个不存在的方法、传一个不存在的参数、用一个已废弃的选项。 它写得非常自信，格式完全正确，只是那个 API 不存在。

检查手段：编译或类型检查。动态语言没有编译期检查，就重点看它引用的库函数—— 跳到定义看一眼，或者直接跑一遍。

三、过度防御 / 过度简化

两个相反的极端，都很常见：

表现为什么是问题
给每行都套 try-catch捕获后只打日志或返回默认值，把错误吞掉了
加一堆没用的参数校验掩盖了真正的入口校验缺失
为了"简洁"删掉边界检查空值、越界、除零，运行时才炸
把复杂逻辑简化成一行可读性提升，但丢了原逻辑的某个分支

检查手段：搜 catch / except / recover， 逐个看它捕获后做了什么。只打日志然后继续的，基本都是错的。

四、风格漂移

命名、错误处理方式、日志格式、导入顺序和你项目既有风格不一致。 单看没问题，放在一起像两个人写的。

检查手段：看新增代码有没有复用你项目里已有的工具函数。 如果它自己又写了一个 formatDate，而项目里已经有一个，就是漂移。

五、看起来对的边界处理

最危险的一类，因为不报错。

类型典型错误
off-by-one< 写成 <=，循环多走一次
空值只判 null 不判空字符串 / 空数组
并发读写之间没有锁，测试环境永远不复现
时区本地时间当 UTC 存
分页最后一页多查一次，或者第一页 offset 算错

检查手段：问它"这段在边界情况下会怎样"，让它自己列出可能的输入。 它列不出来的，你补上测试。

按风险排序的检查顺序

15 分钟内该按什么顺序看？从"机器能告诉你的"开始，越往后越需要人判断。

顺序检查项耗时能抓出什么
1编译 / 类型检查秒级编造 API、漏改签名
2跑现有测试秒到分行为回归
3grep 被改动的标识符1 分钟漏改调用方
4看 catch 块做什么2 分钟吞异常
5看边界条件5 分钟off-by-one、空值
6看风格一致性2 分钟重复造轮子
7看全局影响剩余架构层面的问题

前四是机器活，应该自动化。把它们做成提交前钩子，你只需要看后三步。

三类必须人工逐行看

其余可以抽查，这三类不行——因为错了不会报错。

类别为什么必须逐行
认证 / 加密 / 权限写出来的代码能跑，但可能有越权或弱加密。不报错，只会在某天被利用
金额 / 库存 / 计数浮点精度、并发扣减、幂等性——错一分钱也是错，且对账才发现
对外契约API 协议、SDK 签名、数据格式。一旦被下游依赖，改的成本是十倍

这三类不要用便宜档模型写，也不要跳过人工审查。 具体选型见 该用哪个模型 与 国产模型边界。

让 AI 自己暴露问题

与其你去找它的错，不如让它先自查。三个有效的问法：

问法一：列出所有受影响的位置

你刚才改动了 X。请列出项目中所有引用 X 的位置，
包括测试、配置文件、文档示例。不要修改，只列出。

它列出来的，你去核对；它漏掉的，正好就是缺陷所在。

问法二：列出这段代码最可能出错的地方

请指出这段实现里最可能出问题的三个地方，
按可能性排序，并说明触发条件。

好的模型能给出有价值的自我批评；差的模型会说"这段代码没有问题"—— 这本身就是个信号。

问法三：假设它是错的

假设这段代码存在一个 bug，最可能是什么？
给出能复现它的具体输入。

这个问法比"检查一下有没有 bug"有效得多，因为后者会得到"看起来没问题"。

一个 15 分钟的流程

  1. 0-1 分钟：跑编译和测试。红的就是全部问题清单
  2. 1-3 分钟：grep 改动过的标识符，看还有哪些引用没跟着改
  3. 3-5 分钟：搜异常处理，检查有没有吞掉错误
  4. 5-10 分钟：让它自己列出边界情况和最可能出错的地方
  5. 10-13 分钟：针对它列出的点，补测试或者验证一次
  6. 13-15 分钟：确认没有落到"必须逐行看"的三类里

超过 15 分钟还没看完，说明这次改动太大了。下次让它拆成更小的步。
