团队共用一套 API Key 的四个坑

「先用一把，回头再拆」通常会变成永远不拆。

四个坑

1. 用量无法归属到人 最常见

月底看到账单涨了三倍，但不知道是谁在用。多见于团队刚开始用 AI 编程工具的那两个月。

2. 一处泄露，全员失效

key 写进了某个公开仓库、贴进了聊天群、或者留在某人的 shell history 里。轮换时全团队一起停工。

共用 key 还意味着：泄露后你无法判断是哪个人、哪个项目漏出去的。

3. 并发与速率上限是共享的

多数中转站按 key 计速率（RPM/TPM）。一个人跑批量任务，其他人的交互式请求就开始 429。这类问题最难排查——因为每个人单看都正常。

4. 离职后收不回来

共用 key 没法「只收回某个人的权限」，只能整体轮换，然后通知所有人改配置。实际执行时经常拖到出事才做。

正确做法：两层 key

不是简单地「一人一把」，而是按人 + 按项目两层：

  • 个人 key：用于交互式使用（编辑器插件、CLI 临时调试），一人一把，设月度额度。
  • 项目 key：用于线上服务与批处理，一个服务一把，设硬上限与告警。

这样「谁在用」和「花在哪」两个问题都能回答。

额度怎么设

  • 个人 key：近三个月用量的峰值 × 1.5，超出说明该人工作量变化或有人在滥用。
  • 项目 key：按预算设硬上限，到 80% 告警、100% 停止。
  • 临时 key：验证性任务单独开一把，用完即删，别设长期有效期。

额度不是越小越安全。设太紧会让人私下去找别的站，反而失去可见性。

配置示例

把 key 从代码里彻底拿出来，用环境变量或密钥管理服务：

# 个人使用：写进 shell 配置，不要写进项目文件
export ANTHROPIC_BASE_URL="https://api.97wl.cc"
export ANTHROPIC_AUTH_TOKEN="$TEAM_KEY_ALICE"

# 线上服务：由部署平台注入，不要出现在仓库里
# .env 加入 .gitignore，CI 用 secrets

# 检查有没有漏在仓库里
git grep -nE "sk-[A-Za-z0-9]{16,}" || echo "clean"

最后那条命令建议加进 pre-commit hook，成本几乎为零。

轮换怎么做得不痛

  1. 所有 key 通过环境变量注入，轮换就是改一个值。
  2. 保留「新旧两把同时有效」的过渡窗口（多数面板支持多 key 并存）。
  3. 轮换后一周内检查旧 key 是否还有调用，有就是漏改的地方。

做到这三条，轮换从「半天停工」变成「改配置 + 重启」。

关于示例端点

本矩阵示例统一用 https://api.97wl.cc/v1。它的面板支持创建多把 API key 与查看用量，适合按上面的两层结构拆分；具体额度与并发上限以站点后台实际展示为准。
