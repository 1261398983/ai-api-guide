上下文工程 · 2026-11-07

怎么给 AI 提供有效上下文

上下文不是越多越好。塞满了它反而记不住关键的那几条。

先破除一个直觉

直觉是：信息给得越多，回答越准。

实际是倒 U 型：给太少它不知道你在说什么；给太多，关键指令被淹没在无关内容里。

这个现象叫上下文稀释。你的规则文件写了 3000 字， 它可能只记住了开头两条和最后一条——中间的被稀释掉了。

信息量结果
太少（只说"改这个函数"）改得不符合项目约定
刚好（规则 + 目标文件 + 相关接口）准确率高
太多（整个仓库 + 三千字规则）关键约束被稀释，还多花钱

三层结构：把信息放到对的位置

有效的上下文不是一坨，是分层的。每层的生命周期和更新频率不同。

层内容更新频率放哪
规则层项目约定：命名、错误处理、目录结构、禁止事项很少变CLAUDE.md / .cursorrules
任务层这次要做什么、验收标准是什么每轮变对话内容
参考层相关文件、接口定义、示例代码按需让它自己去读，或贴关键片段

最常见的问题是把参考层的内容塞进规则层。 规则文件里贴了 20 个代码示例，每次请求都重发，既贵又稀释。

规则文件该写什么

判断标准只有一条：这条不写，它就会写错吗？

会，才写。不会，就别占用预算。

该写的（四类）

类别例子
反直觉的约定「本项目错误统一用 Result 类型，不抛异常」
禁止事项「不要引入新的第三方依赖」「不要改 migrations 目录」
入口位置「API 路由在 src/routes/，每个文件导出一个 router」
验证方式「改完跑 make test，不要跑全量」

不该写的（四类）

类别为什么不该写
它默认就会做对的事「请写规范的代码」「注意错误处理」——废话，白占预算
代码示例占地方且容易过时；需要时让它读实际文件
历史变更记录「v1 用的 X，v2 改成 Y」——它只需要知道现在是什么
完整目录树几十行路径，它记不住也用不上

一个克制的模板

# 项目约定

## 结构
- API 路由：src/routes/*.ts，每文件导出一个 router
- 业务逻辑：src/services/，不直接碰 DB
- 数据访问：src/repo/，所有 SQL 在这里

## 必须遵守
- 错误统一用 Result<T, E>，不抛异常
- 新增依赖前先问，不要自作主张
- migrations/ 目录只读，不要改历史迁移

## 验证
- 改完跑 `make test-unit`（约 20 秒）
- 不要跑全量测试，太慢

## 禁止
- 不要用 any
- 不要写 console.log，用 logger

这个模板约 200 字。如果你的规则文件超过 1000 字， 先问自己：删掉哪些，它仍然不会写错？

参考层：让它自己读，不是全塞进去

正确做法不是把相关文件内容贴进对话，而是告诉它去哪读。

❌ 贴进来
以下是 UserService.ts 的全部内容：（800 行）
以下是 UserRepo.ts 的全部内容：（600 行）
请修改用户昵称的校验逻辑

✅ 指路径
修改 src/services/UserService.ts 里的昵称校验。
校验规则参考 src/utils/validators.ts 里已有的实现，
数据访问走 src/repo/UserRepo.ts 的 updateUser。

好处有三：省 token、它读的是最新版本、以及它会自己找到你没提到的依赖。

什么时候该贴？这段代码它读不到——比如报错堆栈、日志片段、 或者不在仓库里的第三方接口文档。

会话管理：什么时候该重开

多轮对话里，每一轮都会重发全部历史。这意味着前面的错误结论会持续污染后续判断。

四个应该重开的信号

信号为什么
换了不相关的任务上一个任务的上下文全是噪音
连续两轮修不好同一个问题它已经在错误的思路上越走越远
你已经纠正它三次以上纠正记录本身成了负担，它开始围绕你的措辞猜
它开始重复之前说过的话上下文接近饱和，开始打转

重开时怎么保住有用信息

不要复制整段对话。提炼成三句话：

背景：这是一个 Express + Prisma 项目，用户模块在 src/services/UserService.ts。
已确认：昵称校验应该复用 validators.ts 里的 validateNickname，
        不要新建一套规则。
目标：改 UserService.ts 的 updateProfile，让它调用 validateNickname。

三句话的信息密度，比两百轮对话高。

上下文污染的四个来源

来源表现处理
失败尝试它试过三种错方案，第四种还是绕着那三条转重开会话，只描述正确方向
错误的既有结论早期你随口说"应该是 X 的问题"，它一直按 X 排查明确说「X 已排除」
过大的文件内容贴了 800 行代码，真正相关的 20 行被淹没只贴相关片段 + 文件路径
无关的历史任务会话里做过五个不相关的事一任务一会话

第一条最隐蔽：它不会告诉你"我之前试错了"，只会继续在错的思路上加码。

一个可复用的提问结构

把一次请求写成五段，比写一大段话有效：

【目标】一句话说明要达成什么
【范围】改哪个文件/函数，不要碰什么
【约束】必须遵守的约定（错误处理方式、依赖限制）
【参考】去哪读相关代码，不要贴全文
【验收】怎么算完成（测试命令、预期行为）

不一定要写这么正式，但心里要有这五段。 缺哪段，它就会在那方面猜——而猜错的部分，正是你要返工的部分。
