该用哪个模型

不是所有任务都值得上最强模型。分三档之后，账单会告诉你差别。

先给结论：按任务分三档

档位任务特征典型场景选谁
重推理要理解全局、跨文件、长链条架构设计、多文件重构、疑难 bug、从零搭项目Opus 档 / GPT 高配 / Gemini 长上下文
日常局部改动、需要一定理解加功能、改接口、写组件、读代码回答问题Sonnet 档（默认主力）
机械规则明确、不需要判断改名、补日志、格式转换、生成样板、写测试桩Haiku 档 / DeepSeek

大部分人的钱是这么浪费的：拿重推理档的模型干机械活。改个变量名、加行日志也走 Opus， 一天下来账单翻三倍，质量一点没提升。

具体型号一直在更新，看思路不看名字：每一代通常都有「强 / 中 / 快」三档， 选型逻辑不变。模型清单以 curl /v1/models 返回的为准。

四个真正拉开差距的地方

1. 长上下文里的细节保持

给它 30 个文件让它改其中一处，能不能记住另外 29 个文件的约定（命名、错误处理风格、导入顺序）。 这一项上强模型和中等模型差距很小，中等模型和轻量模型差距很大。

判据：让它在不提醒的情况下，沿用你项目里已有的错误处理方式。做不到就说明上下文保持不够。

2. 跨文件的一致性

改一个接口，相关的调用方、类型定义、测试要不要一起改。 轻量模型经常只改被点到的那一处，留下十几处编译不过的引用。

判据：让它改一个被多处引用的函数签名，看它会不会主动去找调用方。

3. 工具调用的稳定性

在 agent 模式下，模型要按格式输出工具调用。格式错一次，整轮就废了。 便宜模型在这上面的失败率明显更高，重试本身也是成本。

4. 对「不知道」的诚实度

遇到不确定的地方，是编一个看起来合理的实现，还是说"这里需要确认"。 这一项直接决定你要花多少时间 review，比跑分重要得多。

混合用法：省一半以上

最省钱的做法不是找最便宜的模型，是让每个任务落到对的档位。

阶段用什么为什么
理解需求、拆任务日常档这一步错了后面全错，值得用好一点
设计整体方案重推理档架构判断错，改起来最贵
批量写样板代码机械档规则明确，好模型没有额外收益
核心逻辑实现日常档需要理解上下文，但不需要全局推理
疑难 bug 定位重推理档需要跨文件追踪调用链
写测试、补注释机械档典型的规则活
最后 review重推理档让它挑毛病，比让它写更值

实际执行时不必这么细。一个够用的近似：默认日常档，遇到卡住超过两轮就切重推理，机械活显式切机械档。

五个常见误区

1. 「贵的模型写代码一定更好」

只在需要长链条推理的任务上成立。改个字段名、加个 try-catch，强模型和轻量模型输出几乎一样， 但价格差几倍到几十倍。

2. 「用便宜模型省钱」

如果它写出来的东西你要花 20 分钟改，那它不省钱。 真实成本 = token 费用 + 你的时间，后者通常更贵。

3. 「模型越大上下文越长」

上下文窗口和模型强弱是两件独立的事。Gemini 的长上下文优势在"把整个仓库读进来"这类场景， 不在"写代码更强"。

4. 「一次切换终身使用」

模型迭代很快，半年前的最强可能现在是中档。定期用同一批任务重测，别凭印象。

5. 「便宜的中转站一定偷换了模型」

会被换，但不是必然。验证方法很简单：发一个请求，看返回 JSON 里的 model 字段和你请求的是否一致。 不一致就是换了上游。七个可查信号里有完整验证命令。

切换模型的操作

不用改端点，只改模型名。以 Claude Code 为例：

# 会话中切换（多数工具支持 /model 或等价命令）
/model sonnet

# 或用环境变量固定
export ANTHROPIC_MODEL="claude-sonnet-4-20250514"

# 先确认这个端点到底提供哪些模型
curl -s "https://your-endpoint.example.com/v1/models" -H "Authorization: Bearer 你的Key" | head -40

切换后先跑一个小任务验证，别直接上大任务——模型名写错时，报错信息往往是 model not found，很容易被误判成网络问题。

模型名与端点实际提供的不一致时，见 错误码对照。
