中转站能看到你的什么：数据流向、可见范围与五条自查

2026-10-24 · 先把链路讲清楚，再谈能不能用
一句话结论：任何中转站在解密后都能完整看到你的 prompt 和模型回复，包括你贴进去的代码。HTTPS 保护的是「传输过程」，不是「服务端处理」。这不是某一家的问题，是这条链路的固有属性。

一、数据流向

你的编辑器 / CLI
   │  ① 明文请求，本地加密
   ▼
[TLS 隧道]  ← 这一段是加密的
   │
   ▼
中转服务器  ← ② 解密后拿到完整明文
   │  ③ 转发给上游
   ▼
上游服务商（OpenAI / Anthropic / Google …）
   │
   ▼
回复沿原路返回

关键在第 ② 步：中转是链路的终点而不是「管道」。加密只在传输层存在，到了服务器必须解密才能转发。

二、中转方能看到什么

可见说明
完整 prompt你的提问、贴进去的代码、报错栈、文件内容
完整回复模型输出的一切
你的 key 与账户用于鉴权与计费，通常以哈希或明文存储
请求头与元数据User-Agent、客户端版本、时间戳、IP
调用模式频率、模型选择、token 用量、失败重试

看不到的

  • 你的本地文件系统（除非你主动把内容发出去）
  • 你机器上别的密钥、浏览器数据
  • 其他客户的数据（除非实现有严重缺陷）
常见误解：「我用了 HTTPS，所以安全」。HTTPS 防的是链路上被第三方窃听，防不了端点自己记录。判断安全性的正确问题不是「有没有 HTTPS」，而是「端点是否记录、记录多久、谁能看」。

三、五个该问的问题

问题为什么重要
请求内容是否落盘？落盘就有泄露与调取风险；只在内存透传风险低一个量级
留存多久？「永久保留用于审计」和「24 小时滚动删除」完全不同
谁能访问日志？运维全员可见 vs 仅故障排查时授权
是否用于训练或转售？上游政策决定，但中转方应能明确回答
有没有独立 key 与额度隔离？决定泄露影响面，见 团队 Key 管理

这五个问题，正规服务商会在文档里写清楚；问不出答案的，按「全记录」对待即可。

四、五条可执行的自查与缓解

1. 按用途分 key，不用同一个

一个 key 泄漏只影响一个场景。多数面板支持建多个子 key 并各自设额度，用完即删。

# 泄露后 30 秒内止血：到面板删除该 key，而不是改密码
# 改密码对已泄露的 key 无效

2. 发出去之前先脱敏

让 AI 帮你看代码时，先替换掉真正的密钥、内网地址、客户标识：

# 常见的无意泄露
sk-live-xxxxxxxx          →  REDACTED_KEY
10.20.30.40:5432          →  DB_HOST:PORT
customer_id=8842          →  customer_id=CUSTOMER_A

更省事的做法是在项目里维护一个忽略清单（.gitignore 的思路），让工具不去读 .env、*.pem、id_rsa。

3. 检查你的规则文件有没有把敏感信息带进去

CLAUDE.md / .cursorrules / .aider.conf.yml 里的内容会被一并发送。有人在这里写了内部 API 地址和测试账号，等于每次请求都在上传。

4. 分级使用，而不是一刀切

数据级别建议
公开代码 / 通用问题随便走，风险可忽略
内部业务代码（无客户数据）可用，但要脱敏密钥与内网地址
客户数据 / 未公开算法 / 密钥不要走第三方明文链路

5. 用行为差异做一次小验证

同一段 prompt 分别发两次，观察响应头里有没有请求 ID、返回是否稳定。正规中转通常有可追踪的请求 ID——不是为了给你看日志，而是说明它有正经的转发实现，而不是简单脚本。

五、和官方 API 比，风险差在哪

维度官方直连中转
数据可见方1 家（上游）2 家（上游 + 中转）
合同与管辖明确的服务条款多为平台公告，约束力弱
泄露影响面取决于上游多一层，且中转侧安全水平不可审计
成本官方价通常更低

结论不是「别用」，而是把「省下的钱」和「多一层可见方」放在一起权衡。公开代码、学习场景、个人项目，这一层风险通常可以接受；客户数据和生产密钥，通常不必冒。
