Token 花得比预期快？四个真实原因与减法清单

2026-10-24 · 先算清钱花在哪，再谈省

多数人的第一反应是「是不是被多扣了」。先别怀疑计费——绝大多数情况是输入 token 涨得比你想象快，而输入部分往往占账单的大头。

一、原因一：上下文重传（最主要的那个）

对话式 API 是无状态的。服务端不记得你上一轮说了什么，客户端必须每次把完整历史重新发过去。

假设每轮对话平均产生 800 token（你的问题 + 模型回复）：

轮次本次发送的输入 token累计输入
第 1 轮约 800800
第 5 轮约 4,00012,000
第 10 轮约 8,00044,000
第 20 轮约 16,000168,000

20 轮对话实际消耗的输入是总字数的 10 倍以上。这不是谁在偷扣，是无状态协议的结构性成本。

推论：一个 20 轮的对话，比 2 个 10 轮的对话贵得多。任务做完就新开对话，是最简单也最有效的省钱动作。

二、原因二：规则文件与工具 schema 膨胀

CLAUDE.md、.cursorrules、系统提示、以及所有 MCP 工具的 schema，都会每轮完整注入。

内容大致 token20 轮额外成本
空规则0—
3000 字规则文件约 1,800约 36,000
8 个 MCP 工具 schema约 2,500约 50,000
两者叠加约 4,300约 86,000

最容易被忽略的是「装了但不用的 MCP」——工具定义照样每轮发送。一个装了几十个工具的配置，光是 schema 就能吃掉大半输入预算。

怎么查

# Claude Code 里可以直接看当前上下文的占用
/context

# 看规则文件到底多长
wc -c CLAUDE.md .cursorrules 2>/dev/null

三、原因三：缓存没命中

主流服务商都支持 prompt caching，命中后输入价格通常便宜到 1/10。但缓存有严格条件：

条件说明
前缀完全一致缓存按前缀匹配，中间改一个字就全失效
静态内容在前把规则、文档、示例放前面；把用户问题放最后
命中窗口内多数实现有 5 分钟级 TTL，隔久了要重新写缓存

常见错误：把时间戳、随机 ID、当次文件名放在 prompt 最前面——每次都不一样，缓存永远命中不了，还白付了缓存写入的溢价。

# ❌ 动态内容在前，缓存必失效
[2026-10-24 19:31:07] 当前文件：main.py


# ✅ 静态在前，动态在后

当前任务：审查 main.py（时间：19:31）

四、原因四：重试放大

超时重试、429 退避重发、流式中断后重来——每一次都会产生新的计费请求，即使你最终只看到一份输出。

场景实际计费
429 后立即重试 3 次最多 4 份输入（失败请求通常也计输入）
60 秒超时 + 自动重发2 份输入 + 可能 1 份输出
流式断在第 90 秒重来前一次的输入全额计费，输出可能按已生成部分计

所以「重试」不是免费动作。正确的做法是：拉长超时而不是立即重试，并给重试加指数退避与上限。

# 典型的错误写法：无退避、无上限
for i in range(5):
    try: return call()
    except: continue

# 正确：指数退避 + 只对可重试错误 + 有上限
backoff = 1
for attempt in range(3):
    try: return call()
    except RateLimit as e:
        time.sleep(backoff); backoff *= 2

五、减法清单（按收益排序）

  1. 任务做完就新开对话 —— 单这一条通常能省一半以上
  2. 裁剪规则文件 —— 只留必须的约束，删掉背景介绍和历史决策记录
  3. 卸载不用的 MCP / 插件 —— schema 是每轮都发
  4. 按任务选模型 —— 改错别字不必用最强模型
  5. 静态内容前置以命中缓存 —— 顺序错了等于没开缓存
  6. 长任务用 /compact 或摘要替换历史 —— 把 10 轮压成 1 段摘要
  7. 批量场景改异步批处理 —— 多数服务商的 batch 接口有折扣
  8. 重试加退避与上限 —— 避免一次抖动变成四次计费

六、怎么估算自己的真实花费

别用「字数 ÷ 4」估——中文与代码的 token 密度差很多。直接看返回体里的 usage：

{
  "usage": {
    "prompt_tokens": 12480,
    "completion_tokens": 512,
    "prompt_tokens_details": { "cached_tokens": 0 }
  }
}

cached_tokens: 0 说明缓存没命中；prompt_tokens 远大于当轮字数说明历史重传在膨胀。这两个数字能定位绝大多数「钱花得莫名其妙」的情况。
