选型判断 · 2026-11-07

国产大模型写代码够用吗

不比较跑分，只讲边界。跑分会过时，边界不会。

先说清楚一件事

「国产模型行不行」这个问题问错了方向。

正确的问法是：我手上这类任务，落在它的能力边界内还是外？

同一批模型，做单文件 CRUD 和做跨模块重构，结论可能完全相反。 所以下面按任务类型分，不按模型排名分。

具体型号迭代很快，本文不给型号推荐。判断框架是稳定的， 换一代模型只需要重新确认一遍边界在哪。

第一类：能放手让它做的

特征是规则明确、影响范围局限在单个文件、结果容易验证。

任务为什么能做
单个函数的实现输入输出明确，跑一遍就知道对不对
CRUD 接口与数据层模式固定，重复度高
脚本、数据处理、格式转换一次性的，错了重跑就行
写测试、补注释、写文档不需要判断，只需要覆盖
样板代码（表单、列表、分页）结构固定，改字段名就行
正则、SQL、shell 命令可即时验证
报错信息解释与修法建议不需要动代码，只需要解释

这一类可以放心用便宜的档位。省钱幅度最大，质量损失最小—— 因为任务本身不需要"理解全局"。

第二类：要盯着看它改的

特征是涉及多个文件、有隐蔽的耦合、错误不会立刻暴露。

任务风险在哪
改一个被多处引用的函数签名只改定义处，调用方全留着，编译不过
加字段 / 改数据结构序列化、校验、默认值容易漏一处
重构一个模块行为等价性没人验证，测试覆盖不到的地方就埋雷
多文件功能开发各文件风格不一致，命名和错误处理乱掉
处理异步 / 并发竞态问题不会在测试里稳定复现
改第三方库的适配层对库的版本差异理解不足，写出过时 API

判断信号：改完之后，你能不能在 5 分钟内说清"这次改了哪几处、为什么"。 说不清就说明它没理解全局，只是局部缝合。

这一类能用，但必须自己 review 每一个改动点。 省下的 token 钱，可能不够补 review 的时间。

第三类：别让它做

特征：错了代价高、且错误不会立刻暴露。

任务为什么危险
架构与技术选型模型会给你一个"看起来合理"的方案，但不知道你的约束
认证 / 加密 / 权限逻辑写出来的代码能跑，但可能有安全漏洞，且不会报错
疑难 bug 的根因定位容易给出"看起来对"的解释，让你往错的方向查半天
数据库迁移脚本不可逆操作，回滚成本极高
性能关键路径"能跑"和"够快"差得很远，而它只保证前者
对外契约（API 协议、SDK）一旦被下游依赖，改起来代价巨大

这一类的正确用法：让它给候选方案和取舍分析， 由你做决定，再由它执行具体实现。不要让它一步到位给出最终答案。

怎么低成本测出你的边界

不用跑分，用你项目里真实的三件事：

测试一：风格继承

给它一个文件，让它加一个新函数，不要在提示里说明风格要求。 看它会不会自动沿用你项目已有的错误处理方式、命名习惯、导入顺序。

做不到 → 每次都要你重写风格 → 它省的钱不够你改的。

测试二：跨文件追踪

让它改一个被 3 处以上引用的函数签名。不要提醒它去找调用方。

看它会不会主动搜索引用、把调用方一起改掉。只改定义处就是典型的能力不足。

测试三：含糊需求的反应

给一个故意含糊的需求（"优化一下这个查询"），看它是先问"哪个指标慢"， 还是直接动手写一个可能没解决任何问题的版本。

会问的，说明知道自己的边界；直接写的，会在真实项目里给你制造返工。

三个测试花不到半小时，比看十篇跑分文章有用。

成本到底差多少

同任务下，国产模型常见是一个数量级的差距。但要算清三件事：

项说明
倍率不是折扣倍率乘的是站点自定义基准价，不是官方价。详见这里
失败重试二次计费稳定性 80% 意味着平均请求 1.25 次，成本 ×1.25
你的 review 时间最容易被忽略的一项，通常比 token 贵得多

真实成本 = token 费用 + 返工时间。 一个便宜但总写错的模型，可能比贵的更费钱。

推荐的混合用法

阶段用哪档理由
拆需求、写伪代码便宜档这步错了后面全错，但错了容易发现
架构判断强档决策错了改起来最贵
批量实现便宜档规则明确，强档没有额外收益
跨文件重构强档需要全局理解
安全相关代码强档 + 人工审查错误不会暴露
写测试、补文档便宜档典型规则活

分档的执行细节见 该用哪个模型。

一个诚实的补充

国产模型在中文表达上普遍更自然。写中文注释、中文文档、面向国内用户的文案， 这一点是稳定优势，不太随模型版本变化。

如果你的项目需要大量中文文档，这项优势值得单独计算—— 它省的是你润色的时间，不是 token 钱。
